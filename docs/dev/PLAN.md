## 2. 專案願景與核心目標

**主目標**：打造一套 AI coach，能評估「訓練品質」與「身體數據」，並據此給出跑步訓練建議與課表調整。

**次要支撐項目**：Garmin 手錶資料串接——這是為了讓 AI coach 有真實數據可分析的**工作項目之一**，不是專案本身的目的。規劃時的資源分配應以 Phase 3（AI 分析層）為核心，資料工程只是把地基打好。

**使用情境**：目前為個人使用，但憑證管理等設計需預留未來可能公開／多使用者的彈性。

## 3. 整體架構

### 3.1 現況（2026-08-17，Phase 1 已完成的部分）

```
Garmin 官方個人資料匯出（一次性快照，手動申請下載）
  │
  ├─ JSON：DI-Connect-Fitness / Wellness / Metrics / Aggregator
  │    └→ garmin_export_parser.py ─→ activities / daily_wellness / metric_coverage
  │
  └─ FIT（DI-Connect-Uploaded-Files 內約 2 萬個檔）
       └→ fit_parser.py ──────────→ activity_laps（每公里分圈）
          workout_classifier.py       activity_records（逐秒降頻，每 10 秒）
                                      activities.workout_type（自動分類）
                  │
                  ▼
         統一本地 SQLite（含 source / 完整度標記）  ← 已完成，資料已入庫
                  │
                  ▼
         【下一步】dashboard_queries.py（查詢層，含即時計算的恢復關聯）
                  │
       ┌──────────┴──────────┐
       ▼                      ▼
  FastAPI + 本機網頁      （未來）MCP Server
  電腦/手機皆可看           包成 AI 可呼叫的 tools
```

**設計原則**：核心邏輯（資料、規則引擎）與 AI 介面層（MCP/Skill）脫鉤，資料擷取來源本身也做成可替換 adapter——因為 Garmin 的反爬蟲手段會持續變動（garth 於 2026年3月因 Garmin 加入 Cloudflare TLS 指紋辨識而停止維護即為一例）。

**已建立的分層慣例**（後續模組應延續）：純解析/計算函式與 I/O 分離——`garmin_export_parser.py`／`fit_parser.py`／`workout_classifier.py` 皆為純函式不碰資料庫，由 `*_import_runner.py` 負責讀寫。好處是純函式可用合成假資料完整單元測試，不需要真實個人資料。

## 4. 風險與待觀察

- Garmin 反爬蟲手段持續在變（garth 停維護即為前例），MCP/API 方案可能再度失效，架構需保留備援彈性。
- GarminDB、garmin-connect-mcp 皆為第三方維護專案，非官方保證長期可用。
- Strava 缺乏 Garmin 專屬生理指標（HRV、Body Battery、Training Readiness），fallback 期間分析品質會降級，需在 UI/對話中誠實反映。

## 5. 全馬週期化課表模板（Phase 2 規格依據）

> 這是課表產生器要實作的**通用規格**，不含任何個別學員數字。個人化排程屬於輸出成果，見 `output/`（不進版控）。

### 5.1 期別結構（16–20 週）

| 期別 | 佔比 | 目標 | 主要課種 |
|---|---|---|---|
| **Base（基礎期）** | 約 40% | 建立有氧基礎、逐步拉長最長距離、養成規律 | 輕鬆跑為主、LSD 漸進拉長、可加入策力跑（strides）|
| **Build（進展期）** | 約 30% | 導入強度、提升乳酸閾值與跑步經濟性 | 節奏跑（Tempo）、閾值跑、馬拉松配速跑、LSD 續拉 |
| **Peak（巔峰期）** | 約 20% | 最大化專項耐力，模擬比賽情境 | 最長 LSD（含馬拉松配速段）、間歇、補給演練 |
| **Taper（減量期）** | 約 10%（2–3 週）| 消除疲勞、保留體能與神經活性 | 量遞減、強度保留少量短促刺激 |

### 5.2 量進與減量規則

- **週跑量進展**：每週增幅不超過 **10%**（保守情境 5~8%）
- **減量週**：每 **3–4 週**安排一次，量降至前一週的 **70~80%**
- **最長單次距離**：Peak 期最長 LSD 建議達 **30–35 K** 或 **3~3.5 小時**（取先到者），不建議超過
- **80/20 原則**：約 80% 訓練量為低強度，20% 為中高強度
- 任何單次距離的躍升不應超過現有最長距離太多，優先以漸進方式突破

### 5.3 課種定義

| 課種 | 強度定位 | 目的 |
|---|---|---|
| 輕鬆跑（Easy）| 能完整對話 | 有氧基礎、恢復 |
| LSD（Long Run）| 輕鬆至馬拉松配速間 | 專項耐力、補給演練、心理適應 |
| 節奏跑（Tempo）| 舒適的吃力，約閾值配速 | 提升乳酸閾值 |
| 間歇（Interval）| 高強度分段 | VO2max、跑步經濟性 |
| 馬拉松配速跑（MP）| 目標比賽配速 | 配速感建立、比賽模擬 |
| 恢復跑／休息 | 最低強度或全休 | 恢復 |

### 5.4 產生器須支援的變因

- **每週跑步天數可配置**（需支援低至 3 天／週，此時 LSD 佔比與品質課配置需特別處理）
- **交叉訓練（如重訓）納入負荷計算**，並避免連續訓練天數踩到個人恢復上限
- **外部限制窗口**（旅遊、出差、賽事）需能降低強度或跳過，並在前後週自動調整
- **外部課表來源**（如跑團）需能匯入／標記，產生器不可假設自己是唯一課表來源
- **首馬 vs 有經驗**：首馬應加重配速保守性、補給演練、撞牆風險相關安排

### 5.5 配速推算方法

- 以近期比賽成績換算 **VDOT**（Daniels），推導各課種配速區間
- 跨距離推算採 **Riegel 公式**（指數 1.06）；長距離推算應優先採用較長距離的成績為基準
- ⚠️ **成績時效性**：超過數月的成績應視為「已知能力上限」而非當前配速依據，需在 Base 期後安排測驗重新校正
- 環境因素（高溫、濕度、地形）造成的配速衰減屬正常，不應判讀為體能倒退
