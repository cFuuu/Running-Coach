| **FIT 解析提前實作**（2026-08-17） | 原訂延後的 1E 提前到 dashboard 之前做完 | 實測發現 Garmin 匯出 JSON 的 `splits` 是**手動按錶的不規則分段**（10km 只有 2~5 段、含 0km 空圈），266 場中僅 94 場有多於一段。使用者把「單場訓練成效分析」列為最高優先，而該需求靠摘要資料做不到——FIT 檔內才有整齊每公里分圈與逐秒資料 |
| **逐秒資料降頻儲存**（2026-08-17） | 逐秒紀錄以每 10 秒一筆降頻後入庫，不存完整逐秒 | 完整逐秒為 266 場 × 約 9000 筆 ≈ 240 萬列，對畫配速曲線與算心率漂移並無實益。實測降頻後僅 68,884 筆、DB 15.3 MB |
| **訓練後恢復不另存資料表**（2026-08-17） | 「練完隔天 HRV/Readiness 變化」等恢復指標由查詢時即時計算，寫在 `dashboard_queries.py`，不新增 schema | 這是衍生資料而非原始事實，存表會與 `daily_wellness` 形成兩份真相且需同步重算；運算量僅兩張千筆小表 JOIN，無效能理由預存；且「恢復」的定義（看隔天/兩天/週均）之後仍可能隨 Phase 3 調整，寫成查詢函式改定義成本遠低於資料遷移 |
| **運動類型不寫死**（2026-08-17） | 匯入哪些運動、哪些要套用配速分類，皆為 `import_fit_files()` 參數與 CLI 旗標（`--sports`／`--classifiable-sports`），預設只有 running | 使用者要求預留未來匯入其他運動類型。兩者分開是因為：未來匯入騎車時逐圈逐秒仍值得存，但用跑步的配速門檻分類騎車會產生誤導標籤，故「匯入」與「分類」需為獨立開關 |
| **自動分類優先，手動修改延後**（2026-08-17） | 先只做 Garmin 資料的自動分類（一律標 `workout_type_source='auto'`），手動修改的 UI/API 之後再做 | 欄位設計已支援：`workout_type_source` 分 auto/manual，且匯入邏輯已會跳過 manual 紀錄不覆蓋，之後補 UI 不需改 schema |
| **健走／重訓只留整場摘要**（2026-08-17） | 非跑步類活動不解析 FIT 逐秒/分圈，也不做訓練類型分類 | 配速結構分類邏輯對重訓無意義；使用者確認這類活動看整場摘要即可 |
| **Phase 2 模組拆分**（2026-08-18 grill） | VDOT/配速、週期化排程、訓練負荷、恢復判斷各自為獨立純函式模組，最後由 orchestrator 組裝，比照 Phase 1 的 `fit_parser.py`／`workout_classifier.py` 分層慣例 | 各模組輸入輸出明確、可獨立單元測試；Phase 3 AI coach 之後可能只需呼叫其中某幾項（例如只問恢復狀態不用重排課表） |
| **VDOT 成績來源不限比賽、改用心率強度加權**（2026-08-18 grill） | 不用 `workout_type` 篩選候選活動，改成所有活動皆為候選，低強度活動先用心率強度（%HRR）推算等效全力配速再代入 Daniels 公式 | 若只限 race/tempo/interval，Fu 這類活動樣本少的使用者可能長期無候選成績可用；用心率強度加權後任何活動都能提供或多或少的參考訊號，信賴度隨強度调整而非二元篩除 |
| **VDOT 雙軌新鮮度門檻**（2026-08-18 grill） | 短距離成績（5K/10K/間歇）維持 90 天新鮮度門檻；半馬/全馬另設較寬鬆門檻（6–12 個月），超過短門檻但在長門檻內仍可採用（信賴度標記較低），通過門檻的候選再依距離代表性排序取優先 | 長距離成績即使數月未更新，仍代表已驗證的耐力基礎與長距離經驗，與短距離成績的「時效性」意義不同；統一 90 天門檻會不合理地排除掉唯一具長距離代表性的錨點（如 Fu 8 個月前的半馬） |
| **HRmax 可配置參數 + 來源標記**（2026-08-18 grill） | VDOT 引擎的 HRmax 來自 `athlete_profile` 表參數，非寫死；並帶 `hrmax_source` 欄位（`measured`/`observed_estimate`/`age_formula`） | Fu 的 HRmax 尚未實測驗證（見 `output/athlete_profile.md` A-1），需要讓下游（UI/對話層）知道這個估算的信賴等級，但不能因未實測就阻斷計算流程 |
| **訓練負荷自建簡化 ATL/CTL/TSB**（2026-08-18 grill） | 不對接 Garmin 現成 Training Load，改自建「距離×強度」（跑步）與「時長×心率強度」（重訓）的 daily load 指標，指數衰減加權平均，兩者共用同一累加池 | Garmin 演算法為黑盒且非每場活動皆有該欄位；自建才能保證公式透明、可解釋，且能把重訓負荷正確併入同一套疲勞指標（身體疲勞不分運動類型） |
| **恢復判斷只輸出旗標，不自動改課表**（2026-08-18 grill） | 恢復判斷模組只輸出狀態評分/旗標（如 `readiness: low` + 觸發原因），不自動改寫已產生的 `training_plan` | Phase 2 是純規則引擎，不包含「這種情況該怎麼調整」的判斷力；自動改課表屬於 Phase 3 AI 教練的職責範圍 |
| **個人化恢復閥值：人工設定 + 獨立建議函式**（2026-08-18 grill） | 個人化閥值（如連續訓練天數門檻）存 `athlete_profile` 可配置欄位，本輪由人工設定；另新增 `suggest_recovery_threshold(athlete_id)` 分析函式，掃描歷史資料算出建議值供參考，但不自動寫回，須人工確認後才寫入 | 自動學習閥值需要足夠樣本量且屬統計分析，現階段資料量（Fu 規律訓練才剛開始不久）尚不足以支持全自動閉環；但预留分析函式介面，讓恢復模組日後只需換一個輸入來源即可接上 |
| **`training_plan` 保留版本歷史，不覆蓋刪除**（2026-08-18 grill） | 每次產生或調整課表都是新的一批 `training_plan` 列，帶 `is_active`／`superseded_by` 版本標記，不覆蓋刪除舊列 | Phase 3 TODO 已列的「AI 建議 → 實際執行 → 下次分析納入偏差比對」評估回饋迴圈，需要看得到「原計畫 vs 調整後計畫」的差異，覆蓋刪除會讓此迴圈做不了 |
| **外部課表協調本輪僅預留欄位**（2026-08-18 grill） | `training_plan` 表加 `plan_source` 欄位（`generated`/`external`），排程器產生課表時跳過已標記 `external` 的日期，但不設計實際匯入/解析外部課表格式的機制 | P-1（跟團課表整合方式）本身標記為暫緩，Fu 預計 9 月底才報名跟團，尚無實際格式可參考，強行設計匯入機制會是在假設上建構 |
| **訓練方法論分層選用：Higdon 曲線 + Daniels 規則，拒絕 Hansons**（2026-08-25 grill／N-6） | 「課表結構」拆成兩層各自選來源：**量的成長曲線與週頻率**參考 Higdon Novice 1（第一週 24.1K、4 跑+1 交叉+2 休），**長跑佔比／強度分配／品質課上限**用 Daniels 的百分比規則。**明確排除 Hansons**。配速換算（Daniels VDOT+Riegel）、負荷模型（Banister ATL/CTL/TSB）不屬流派選擇，維持現狀 | 一手查證見 [docs/research/training-methodologies.md](../research/training-methodologies.md)。①Hansons 官方教練明述 Beginner 前提為「已能舒服跑 32K/週」且有 5K–半馬經驗，Beginner 尖峰達 88K/週；Hansons 自承 16 英里上限「不是魔術數字」，是從週跑 50–70 英里推導。Fu 週均 15K 時長跑僅該 2.3–2.8K，**cumulative fatigue 在物理上不可能發生**，摘取其長跑上限只會得到「長跑不足的 Daniels」。②Daniels 長跑規則明確在 40 英里線上分岔（<40 mi 取週量 30%；≥40 mi 取 25% 與 150 分鐘較小者），是他預期低量使用者的正面證據；強度上限皆為百分比（80% easy、T≤10%、I≤8%、R≤5%）會自動縮放。③Higdon Novice 1 是四派中唯一在**頻率**上對得上 Fu 的（4 跑/週）。④此分層非「四不像融合」：Higdon 未提出強度分配主張，無規則層可被破壞，故填入 Daniels 規則不拆解任何流派的內部自洽性 |
| **N-6 深入流派比較的重啟條件**（2026-08-25 grill） | 本輪不再進一步比較流派優劣。**重啟條件**：當週跑量穩定 ≥45K 且週練 ≥5 次持續 8 週，N-6 重新開啟評估（屆時 Hansons 才成為真的選項） | 兩派的實質差異（長跑 16 vs 20+ 英里對全馬後半的影響）要在高量、完整週期下才顯現。Fu 2026-01～06 半年僅 17 次跑步、最長 21.2K，**即使跑完一個週期也產生不出能區分兩派的證據**——該實驗設計沒有檢定力，故「先跑一週期再評估」不成立，改以量化門檻當重啟條件 |
| **品質課絕對下限為工程決策，不假託文獻**（2026-08-25 grill） | 訂定品質課主段的絕對下限（暫定 ≥3K 或 ≥12 分鐘），低於此則該週不排該課種、改為全 easy。此下限**明確標註為工程實務決策、無文獻出處** | Daniels 的百分比規則在極低量下產生荒謬輸出：週 15K 時 T 配速上限 10% 僅 1.5K，暖身都不只這個距離。四派文獻均查不到實務下限（見研究文件「查證限制」），故必須自訂；但為守住 N-3「輸出附依據來源」的誠實性，查不到就標查不到，不得假託 Daniels |
| **新增 Phase 0「重建規律期」**（2026-08-25 grill） | 進入 Higdon 週期第一週之前，先設一個以**頻率**為目標的前置期（穩定達到每週 3–4 跑，里程不設要求），連續 3–4 週達標才進正式週期。驗收標準是行為指標而非配速/距離 | Higdon Novice 第一週假設每週跑 4 次，但 Fu 2026-01～06 為每**月** 1–4 次，直接套用第一週的增幅遠超 §6.2「週增量 ≤10%」規則。此期呼應「遵從度獨立為行為指標」的決策——Phase 0 期間遵從度就是主要指標 |
| **Garmin 衍生值為對照組／校準來源，不進事實層**（2026-08-25 grill／N-6 延伸） | 訓練負荷維持自建、**不併入** Garmin 訓練負荷；但恢復模組（§6.7）可將 Garmin `recovery_time_hours`／`training_readiness_score` 的長序列當作**閾值校準參考與背離對照組**。事實層預設不取用黑盒衍生欄位，須明確標記 | ①Garmin 演算法（Firstbeat）為黑盒，無法標出處，違反 N-3 要求。②兩者測的不是同一件事：自建模型用「時長×%HRR」把重訓併入同一累加池（§1 已拍板「疲勞不分運動類型」），Garmin 主要基於 EPOC 且重訓計法不同，**背離時無法分辨是演算法差異還是自己算錯**。③但恢復指標覆蓋 1086 天（2023-08 起），為自建 HRV 序列（292 天）的 3.7 倍，正好補在資料最薄處，當校準來源有實益 |
| **規則層永不自動改寫課表（射程擴大）**（2026-08-25 grill／N-4 前置） | 將 §1 原「恢復判斷只輸出旗標，不自動改課表」的射程從恢復判斷**推廣為通則**：規則層在任何情境下都不自動改寫課表，一律只輸出旗標＋觸發原因。對「持續漏課但生理數據正常」的情境，規則層只標示遵從度，追問原因由對話層負責 | 「練不動（傷病）／沒空練／不想練」三者在資料上長得一模一樣（都是漏課），但正確反應相反。Fu 2026-01～06 每月 1–4 次即為現成案例，從資料無法分辨屬於哪種。若一律自動降量，「不想練」會被系統主動放棄，進入「越練越少→目標越退→更沒動機」的死亡螺旋。判斷「漏課該不該降量」正屬規則引擎不具備的判斷力 |
| **遵從度自訓練品質分數中拆出**（2026-08-25 grill） | 訓練品質評估＝單場生理三維度（配速執行度、心率漂移、恢復是否充足）；**遵從度改為獨立的週期性行為指標**，兩者皆提供給 AI 但**不合成單一分數** | 前三者是「這場練得如何」（單場、生理），遵從度是「這段期間做了多少」（跨時間、行為），性質不同。混入同一分數會導致「沒空練造成的低遵從度，拉低單場其實練得很好的品質評分」。合成單一分數等於把判斷偷渡進事實層 |
| **跟團課表介入時系統退居分析層**（2026-08-25 grill／承 P-1） | 一旦有跟團教練的實體課表，系統**完全停用課表產生**，以跟團課表為唯一基準；系統只保留事後分析（單場品質、恢復判斷、負荷追蹤）。不做「並列建議課表」，也不在跟團未排的日子自動補課 | ①並列建議在權威性上贏不了實體教練，只製造「該聽誰的」噪音。②往空檔補課等於偷偷加量——跟團教練排課時已把休息日算進週期設計，補課會破壞其設計。③呼應 §1 已拍板的 `plan_source` 欄位與「排程器跳過 external 日期」。**注意**：此決策使系統價值全部轉移至分析層，**事實層偏誤的後果因此被放大**，直接提高 §7.4 第 3 點的風險等級 |
| **事實層輸出契約：事實＋依據來源＋信賴度（三者缺一不可）**（2026-08-25 grill／N-4） | §7.3 原框架「AI 拿到的是規則算好的事實＋依據來源」**不足，強制補上第三欄位「信賴度／已知偏誤」**。硬規則：任何事實層輸出若無法附上信賴度標記，**不得輸出**——寧可回傳 `None` 也不給裸數字 | 原框架剝奪了 AI 表達不確定性的能力，然後怪它過度自信。「心率漂移 6.2%」與「心率漂移 6.2%（基於 HRmax=190，手錶顯示值未實測，±5bpm 誤差會讓此值落在 4.8–7.9%）」的差別在於：後者 AI 才能判斷「這數字不夠硬，不該據此建議減量」。**未推翻分層框架**——因為讓 AI 改看原始數據並不更安全（它看到 `acwr: 47` 只是把規則的錯誤語意換成自己瞎猜的語意），問題不在「事實 vs 原始數據」這條軸上 |
| **`workout_type` 為 unknown/NULL 時不輸出類型相關判讀**（2026-08-25 grill） | 該場次**不評**配速執行度等需要課種前提的維度，而非輸出 `unknown` 讓 AI 自行處理。長期解為補人工標註（`workout_type_source` 已支援 `manual`，schema 不需改） | 實測 unknown 45 + NULL 23 = **68/266（25.6%）**，高於原文件記載的 18%。unknown 不是「未知的課種」而是**分類器沉默失敗**——它可能是任何東西。拿 easy 的配速標準去評一場其實是間歇的課，會產出完全錯誤的「執行度不佳」。少評 25.6% 的場次遠優於在 25.6% 的場次上給錯誤判讀，因為錯誤判讀比沒有判讀更難察覺 |
| **HRV 的短期用法與長期基準須分別標記信賴度**（2026-08-25 grill） | 短期變化（vs 7 日均值）標為**可信**；長期個人基準（「你的正常 HRV 是 X」）標為**低信賴、樣本期含訓練中斷**。並以 Garmin 1086 天長序列作偏移對照（非取代） | HRV 僅 292 天（2025-10-25 起），佔 wellness 1651 天的 17.7%。7 日均值不需長歷史故短期比較安全；但個人基準線需跨季節樣本，而該 292 天期間訓練量從 15 次/月掉到 1–4 次/月再回升，基準線是在**訓練狀態劇烈變動中**建立的 |
| **AI 給建議時必須回述所用事實清單**（2026-08-25 grill） | 硬性格式要求：每次建議須列出「本次判斷用了哪幾條事實」（列出輸入，非解釋原因） | 為 §7.4 第 5 點（失敗歸因）的處置。系統退居分析層後唯一產出即判讀，判讀錯誤必須能分辨是事實層算錯或判斷層權衡錯。成本僅在 prompt 層，但讓爛建議變成可除錯；亦是第 4 點（比重如何驗證）唯一入口——沒有輸入回述就無從對照 |
| **閾值輸出數值＋門檻＋門檻適用性，定性由 AI 做**（2026-08-25 grill／N-4） | 事實層不輸出「心率漂移偏高」這類已定性結論，而是輸出「6.2%／文獻門檻 5%／該門檻源自 X 研究、族群為 Y、與本學員條件符合或不符合」，由判斷層決定算不算偏高 | 若閾值歸事實層，等於把「這個門檻適用於你嗎」這個判斷偷藏進事實層；若閾值全歸判斷層，則浪費 N-3 的研究成果、讓 AI 每次重新發明門檻，飄移風險回歸。**門檻的適用性即門檻的信賴度**，故此決策與「事實＋依據來源＋信賴度」三欄位契約是同一個形狀，非額外加規則 |
| **軟性輸入半落地：自由文字＋日期範圍，不做結構化欄位**（2026-08-25 grill／N-4） | 新增 `context_notes`（自由文字 + 日期範圍 + athlete_id），記錄出差／睡眠不足／工作壓力／心情等規則算不出的情境。**不**預先設計類型與嚴重度等結構化欄位。**硬邊界：軟性輸入永不進事實層，僅作判斷層的補充輸入** | ①不落地不可行——§6.8 保留課表版本歷史是為支撐「原計畫 vs 實際執行」的偏差比對迴圈，若「為什麼偏差」只存在對話中，三個月後回看只見「漏了三課」而不見「因為出差」，該迴圈做不完整。②全結構化過早——現在尚不知「嚴重度」該如何分級，硬訂 schema 是在假設上建構（與 §1「外部課表本輪僅預留欄位」同一拒絕理由）。③自由文字讓 AI 讀得懂、日期範圍讓規則層能與活動/wellness 對齊；累積數十筆後回看實際內容再決定是否結構化。④軟性輸入無法驗證（學員自述睡不好，系統無從查證），若參與規則計算等於在事實層開一個沒有信賴度可標的洞，違反三欄位契約的硬規則 |

## 2. 專案願景與核心目標

**主目標**：打造一套 AI coach，能評估「訓練品質」與「身體數據」，並據此給出跑步訓練建議與課表調整。

**次要支撐項目**：Garmin 手錶資料串接——這是為了讓 AI coach 有真實數據可分析的**工作項目之一**，不是專案本身的目的。規劃時的資源分配應以 Phase 3（AI 分析層）為核心，資料工程只是把地基打好。

**使用情境**：目前為個人使用，但憑證管理等設計需預留未來可能公開／多使用者的彈性。

## 4. 風險與待觀察

- Garmin 反爬蟲手段持續在變（garth 停維護即為前例），MCP/API 方案可能再度失效，架構需保留備援彈性。

## 5. 訓練方法論的選擇（✅ 2026-08-25 grill 定案）

> **狀態**：已定案，結論見 §1 決策記錄。一手查證見 [docs/research/training-methodologies.md](../research/training-methodologies.md)。
> **本章結論**：課表結構採**分層選用**——量的成長曲線與週頻率參考 Higdon Novice 1，長跑佔比／強度分配／品質課上限用 Daniels 的百分比規則，**明確排除 Hansons**。

### 5.1 問題的正確層級：不是「選一派」，而是「哪些維度真的有流派分歧」

grill 過程中最先被推翻的，是「單押一派 vs 多派融合 vs 依情境切換」這個框架本身。實際盤點後，四個維度中只有一個存在流派分歧：

| 維度 | 現行做法 | 來源 | 有無流派分歧 |
|---|---|---|---|
| 配速換算（§6.5） | VDOT + Riegel | Daniels / Riegel 1981 | ❌ 無成熟替代品；Hansons/Higdon 未提出自己的換算系統 |
| 訓練負荷（§6.6） | ATL/CTL/TSB | **Banister** impulse-response（1975–1991）→ Coggan/TrainingPeaks 產品化 | ❌ 屬運動生理**數學建模**傳統，四位作者無人提出過負荷量化模型 |
| 恢復判斷（§6.7） | 自建旗標 | 生理學文獻（待 N-3 補出處） | ❌ |
| **課表結構（§6.1／6.2）** | **期別結構 + 長跑上限** | **本章要決定的對象** | ✅ **唯一有分歧處** |

**推論**：專案「早已在融合」，但那不是選擇的結果，而是各維度各有唯一成熟可用解。因此 N-6 的範圍收斂為單一維度——**課表結構**。

### 5.2 一手查證的關鍵發現

完整調查見 [docs/research/training-methodologies.md](../research/training-methodologies.md)，以下為影響決策的三點：

1. **Hansons 有明確准入門檻，且其長跑上限不可摘取**。官方教練 Luke Humphrey 明述 Beginner 課表前提為「已能舒服跑 20 miles/32K 每週」且具 5K–半馬經驗，並直言「It's not necessarily recommended for those who are brand new to running」；Beginner 尖峰達 55 mi/88K。更關鍵的是 Hansons 自承 16 英里上限「**不是魔術數字**」，而是從週跑 50–70 英里的跑者推導（同時滿足「長跑佔週量 25–30%」與 3 小時上限兩條件）。**在週量 15K 下，25–30% 的長跑僅 2.3–2.8K，cumulative fatigue 在物理上不可能發生。**
2. **Daniels 把低量寫進了規則本身**。長跑規則明確在 40 英里線上分岔：**週量 < 40 mi/64K 者取週里程 30%；≥ 40 mi 者取 25% 與 150 分鐘中較小者**。此分支是 Daniels 預期低量使用者存在的**正面證據**。強度上限亦全為百分比（80% easy、T ≤10%、I ≤8%、R ≤5%），低量時自動等比縮小。
3. **Higdon Novice 1 在頻率上是唯一對得上的**。第一週恰為 15.0 mi/24.1K，18 週爬升至 40 mi/64.4K，組成為 4 跑 + 1 交叉訓練 + 2 休息。Hansons（6 天）、Pfitzinger（5–7 天）、Daniels 2Q 的頻率要求均高於現況。**但 Higdon 幾乎無品質課、亦無強度分配主張**，單獨採用撐不起本專案「訓練品質評估」的核心目標。

### 5.3 定案：分層選用

- **量的成長曲線與週頻率** → Higdon Novice 1
- **長跑佔比、強度分配、品質課上限** → Daniels 百分比規則
- **排除** → Hansons（准入門檻未達、機制不成立）、Pfitzinger（週 5–7 練，頻率不符）

**為何這不是 §5.4 第 2 點擔心的「四不像」**：融合的危險在於摘取某流派的參數卻丟棄其成立前提（Hansons 的 16 英里上限即為典型）。但 **Higdon 從未提出強度分配主張，其體系內沒有可被破壞的規則層**——填入 Daniels 的百分比規則不拆解任何流派的內部自洽性。反之若採 Hansons 的長跑上限而不採其週量，得到的不是 Hansons，是「長跑不足的 Daniels」。

### 5.4 兩個必須自行承擔的缺口

1. **Daniels 百分比規則在極低量下失效**：週 15K 時 T 配速上限 10% 僅 1.5K，短於暖身距離。四派文獻均查不到實務下限，故訂定絕對下限（暫定品質課主段 ≥3K 或 ≥12 分鐘）並**標註為工程實務決策、無文獻出處**——見 §1 對應決策。
2. **Higdon 第一週假設每週 4 跑**，而現況為每**月** 4–7 跑。故於正式週期前增設 **Phase 0「重建規律期」**，以頻率（非里程）為目標，連續 3–4 週穩定達到週 3–4 跑後才進入週期第一週。

### 5.5 重啟條件

本輪不再進一步比較流派優劣。**當週跑量穩定 ≥45K 且週練 ≥5 次持續 8 週時，N-6 重新開啟**——屆時 Hansons 才成為真的選項。

> **為何不採「先跑一個週期收集實證再評估」**：兩派的實質差異要在高量、完整週期下才顯現。實測資料顯示 2026-01～06 半年僅 17 次跑步、近 10 個月最長 21.2K——**即使跑完一個週期也產生不出能區分兩派的證據**，該實驗設計沒有檢定力。故改以量化門檻作為重啟條件，而非時間或週期數。

### 5.6 查證限制（誠實聲明）

四本原著全文均未取得。唯一逐字一手文件為 Higdon 官方課表 PDF（逐週加總驗算）。標記為**未能查證**者包括：Pfitzinger 各中週期週數、Pfitzinger 以其本人文字表述的前置里程要求、Hansons 正式期別名稱與強度百分比、Higdon 20 英里上限的理由。上述缺口不得以推測填補，N-3 若需引用須另行查證。

## 6. 全馬週期化課表模板（Phase 2 規格依據）

> 這是課表產生器要實作的**通用規格**，不含任何個別學員數字。個人化排程屬於輸出成果，見 `output/`（不進版控）。

### 6.1 期別結構（16–20 週）

| 期別 | 佔比 | 目標 | 主要課種 |
|---|---|---|---|
| **Base（基礎期）** | 約 40% | 建立有氧基礎、逐步拉長最長距離、養成規律 | 輕鬆跑為主、LSD 漸進拉長、可加入策力跑（strides）|
| **Build（進展期）** | 約 30% | 導入強度、提升乳酸閾值與跑步經濟性 | 節奏跑（Tempo）、閾值跑、馬拉松配速跑、LSD 續拉 |
| **Peak（巔峰期）** | 約 20% | 最大化專項耐力，模擬比賽情境 | 最長 LSD（含馬拉松配速段）、間歇、補給演練 |
| **Taper（減量期）** | 約 10%（2–3 週）| 消除疲勞、保留體能與神經活性 | 量遞減、強度保留少量短促刺激 |

### 6.2 量進與減量規則

- **週跑量進展**：每週增幅不超過 **10%**（保守情境 5~8%）
- **減量週**：每 **3–4 週**安排一次，量降至前一週的 **70~80%**
- **最長單次距離**：Peak 期最長 LSD 建議達 **30–35 K** 或 **3~3.5 小時**（取先到者），不建議超過
- **80/20 原則**：約 80% 訓練量為低強度，20% 為中高強度
- 任何單次距離的躍升不應超過現有最長距離太多，優先以漸進方式突破

### 6.3 課種定義

| 課種 | 強度定位 | 目的 |
|---|---|---|
| 輕鬆跑（Easy）| 能完整對話 | 有氧基礎、恢復 |
| LSD（Long Run）| 輕鬆至馬拉松配速間 | 專項耐力、補給演練、心理適應 |
| 節奏跑（Tempo）| 舒適的吃力，約閾值配速 | 提升乳酸閾值 |
| 間歇（Interval）| 高強度分段 | VO2max、跑步經濟性 |
| 馬拉松配速跑（MP）| 目標比賽配速 | 配速感建立、比賽模擬 |
| 恢復跑／休息 | 最低強度或全休 | 恢復 |

### 6.4 產生器須支援的變因

- **每週跑步天數可配置**（需支援低至 3 天／週，此時 LSD 佔比與品質課配置需特別處理）
- **交叉訓練（如重訓）納入負荷計算**，並避免連續訓練天數踩到個人恢復上限
- **外部限制窗口**（旅遊、出差、賽事）僅定義成「日期範圍 + 限制等級」（`reduced`/`skip`/`flexible`），具體哪天跑、跑多少仍由排程器在窗口內依常規規則排（只是強度上限降低），不需使用者預先指定哪天能跑
- **外部課表來源**（如跑團）需能匯入／標記，產生器不可假設自己是唯一課表來源——本輪僅預留 `plan_source`（`generated`/`external`）欄位與跳過邏輯，實際匯入/解析機制待 P-1 有真實格式可參考時再設計
- **首馬 vs 有經驗**：參數化為 `is_first_marathon: bool`，驅動生成邏輯內的條件分支（非另建獨立模板）——影響 (1) 配速區間自動加保守緩衝、(2) Peak 期自動標記至少 1–2 次「長距離含補給演練」日，日後有經驗跑者也能沿用同一產生器

**輸出頸粒度**：排程器輸出到**單日級別**（日期、課種、目標距離/時間、配速區間、預期心率區間），而非只到週級別總量，以支援之後逐日比對實際執行（`activities`）的遵從度。

### 6.5 配速推算方法

- 以**任何活動**（不限比賽成績）換算 **VDOT**（Daniels）：低強度活動先用心率強度（%HRR）推算等效全力配速，再代入 Daniels 公式；HRmax 為可配置參數（`athlete_profile`），帶 `hrmax_source` 信賴度標記
- **雙軌新鮮度門檻**：短距離成績（5K/10K/間歇）90 天內；半馬/全馬另設較寬鬆門檻（6–12 個月）。通過各自門檻的候選中，再依距離代表性排序取優先（半馬/全馬 > 10K > 5K > 短間歇）
- 跨距離推算採 **Riegel 公式**（指數 1.06）
- ⚠️ **成績時效性**：超過門檻的成績直接排除、不參與加權（非降權混合），避免配速依據來源不透明；「無新鮮成績可用」專指全新手錶、零活動紀錄的情境，此時課表產生器需要明確的必要輸入或保守退回策略（待實作時依實際情境決定）
- 環境因素（高溫、濕度、地形）造成的配速衰減屬正常，不應判讀為體能倒退

### 6.6 訓練負荷模型

- 自建簡化版 **ATL/CTL/TSB**，不依賴 Garmin 現成 Training Load（黑盒公式、非每場活動皆有該欄位）
- 跑步：距離 × 強度；重訓：時長 × 心率強度（%HRR），兩者歸一到「時長×強度」共同基礎，共用同一累加池（總 ATL/CTL）——身體疲勞不分運動類型
- 若重訓活動連心率都沒有，用固定保守估計強度並標記不確定

### 6.7 恢復判斷邏輯

- 恢復判斷模組只輸出**狀態評分/旗標**（如 `readiness: low` + 觸發原因），不自動改寫已產生的 `training_plan`——實際要不要調整、怎麼調，由使用者或 Phase 3 AI 教練依評分決定
- 個人化恢復閥值（如「連續 N 天訓練即 HRV 明顯偏低」）存 `athlete_profile` 可配置欄位，本輪由人工設定
- 另建獨立分析函式 `suggest_recovery_threshold(athlete_id)`，掃描歷史 `daily_wellness`＋`activities` 算出建議閥值供參考，**不自動寫回**，須人工確認後才寫入 `athlete_profile`

### 6.8 輸出與版本化

- `training_plan` 表**保留版本歷史**：每次產生或調整都是新的一批列，帶 `is_active`／`superseded_by` 版本標記，不覆蓋刪除舊列——支援「原計畫 vs 調整後計畫 vs 實際執行」的偏差比對（呼應 Phase 3 的評估回饋迴圈）

### 6.9 驗證策略

- 以**不變量式單元測試**為主：對每個規則（進量不超 10%、減量週降至 70–80%、期別佔比、週天數不足時 LSD/品質課配置）寫斷言式測試，並對輸入參數空間（週數、週天數組合）做範圍性測試
- 不以 Fu 的真實 17.9 週課表當自動驗收標準（屬使用者主觀評判），但可手動展示供其確認「看起來合理」

## 7. 事實層與判斷層的分工（Phase 3 規格依據，✅ 2026-08-25 grill 定案）

> **狀態**：已全數定案（§7.1–§7.5），結論已移入 §1 決策記錄。§7.6 風格層為另案擱置，不在本次範圍。
> **前提變更**：§1 已拍板「跟團課表介入時系統退居分析層」——系統不再產生課表，**價值 100% 押在判讀上**。事實層若有偏誤，沒有第二個產出可以遮掩。此變更顯著提高本章的風險等級。

### 7.1 問題的正確形式

這**不是**「規則引擎 vs 丟給 AI 分析」的二選一，而是一條連續光譜上要把界線畫在哪：

| 位置 | 規則引擎負責 | AI 負責 |
|---|---|---|
| 純 AI 派 | 無 | 拿原始數據，全部自行判讀 |
| 目前現況 | readiness（low/normal）、VDOT 配速推算 | 其餘全部臨場判讀 |
| **本次定案** | **事實＋依據來源＋信賴度**（三者缺一不可） | 綜合旗標、權衡情境、溝通 |
| 極端規則派 | 連「該怎麼調課表」都寫死 | 只把規則輸出翻成人話 |

### 7.2 兩端各自的成本（皆非零成本）

**純 AI 派的隱性成本**——表面省下寫規則的工，實際把成本轉移到別處：
- **無法驗證**：規則引擎可寫單元測試（現有 301 項），AI 判讀無法用 assert 檢查
- **不可重現**：同一份數據不同天問可能得到不同判讀。作為教練此為致命傷——「上週說沒問題，這週怎麼說我練太多？」
- **無法解釋依據**：只能事後生成一個聽起來合理的理由，與 N-3 要求的「輸出附依據來源」互斥

**純規則派的成本**——僵化。真實教練會做多因素情境權衡（「配速掉了但剛出差回來、睡眠只有 5 小時」），這類權衡寫成規則會組合爆炸，而 AI 恰好擅長。

### 7.3 定案框架：事實 ＋ 依據來源 ＋ **信賴度**

核心主張「這場練得好不好」可以拆開仍然成立：

- **事實層（規則引擎）**：配速較目標慢 8%、心率漂移 6.2%、當日 readiness 為 low、連續第 4 天訓練——可計算、可測試、可重現
- **判斷層（AI coach）**：綜合上述事實，加上規則算不出的情境（出差、睡眠、心理狀態、賽事剩餘週數），給出建議並解釋原因

**但原框架「事實＋依據來源」不足，必須補上第三欄位。** 見 §7.4 的論證。定案後的契約為：

```
事實層輸出 = { 數值, 依據來源, 信賴度/已知偏誤 }
```

**硬規則：任何事實層輸出，若無法附上信賴度標記，就不得輸出——寧可回傳 `None`，也不給裸數字。**

理由：現行框架剝奪了 AI 表達不確定性的能力，然後怪它過度自信。對照兩種輸出——

- ❌「心率漂移 6.2%」
- ✅「心率漂移 6.2%（基於 HRmax=190，來源：手錶顯示值未實測；±5bpm 誤差會讓此數字落在 4.8–7.9% 之間）」

後者 AI 才有辦法做出「這個數字不夠硬，我不該據此建議減量」的判斷。

### 7.4 錯誤事實的放大風險（原 §7.4 第 3 點，✅ 已處理）

**此爭點成立，且已有實際發生的案例。** 實測資料盤點：

| 被稱為「事實」的輸出 | 實際狀況 | 偏誤性質 |
|---|---|---|
| `workout_type` | unknown 45 + NULL 23 = **68/266（25.6%）** | 分類器對非典型課表**沉默失敗**（原文件記為 18%，低估） |
| HRV 個人基準 | 292 天（2025-10-25 起），僅佔 wellness 1651 天的 **17.7%** | 樣本期不涵蓋 2019–2025 訓練史，且期間訓練量劇烈變動 |
| HRmax | 手錶顯示值，`hrmax_source` 已標記但**尚未實測** | 系統性偏移，方向未知 |
| `acwr` | **語意錯誤，已於 2026-08-25 修正** | Garmin `acwrFactorPercent`（0–100 貢獻度）被標成「急慢性負荷比（ACWR）」 |

**第四列是決定性證據**：這不是假想風險，它已經在系統中存在了一段時間。若未翻查程式碼，AI 會把 0–100 的分數當 0.8–1.3 的比值解讀，產出一段有依據、有出處、格式完美、**內容錯誤**的分析。

**但結論不是「回去讓 AI 看原始數據」**：原始數據不會更安全——AI 看到 `acwr: 47` 一樣不知道那是什麼，只是把「規則的錯誤語意」換成「AI 自己瞎猜的語意」。問題不在「事實 vs 原始數據」這條軸上，而在於原框架**漏掉了信賴度欄位**。故處置為 §7.3 的三欄位契約，而非推翻分層。

**衍生處置**：

1. **`workout_type` 為 unknown/NULL 時，不輸出該場的類型相關判讀**（如配速執行度），而非輸出 `unknown` 讓 AI 自行處理。unknown 不是「未知的課種」，是**分類器失敗**——它可能是任何東西。拿 easy 的配速標準去評一場其實是間歇的課，會產出完全錯誤的「執行度不佳」。少評 25.6% 的場次，遠優於在 25.6% 的場次上給出錯誤判讀（後者更難察覺）。長期解為補人工標註（`workout_type_source` 已支援 `manual`，schema 不需改）。
2. **HRV 的兩種用法須分別標記信賴度**：短期變化（vs 7 日均值）標為**可信**（7 日均值不需長歷史）；長期個人基準（「你的正常 HRV 是 X」）標為**低信賴、樣本期含訓練中斷**。並以 Garmin 的 1086 天長序列作**偏移對照**（非取代），檢查自建基準線與其差異。
3. **AI 每次給建議時，必須回述所用的事實清單**（列出輸入，非解釋原因）。成本僅在 prompt 層，但它讓「爛建議」變成可除錯——看回述清單即可分辨是拿錯數字（事實層）還是想錯（判斷層）。此為原 §7.4 第 5 點（失敗歸因）的處置，亦是第 4 點（比重如何驗證）唯一可能的入口：沒有輸入回述，無從對照。

### 7.5 界線判準：閾值與軟性輸入

**閾值定義本身不歸事實層，也不歸判斷層，而是拆開。** 事實層輸出三件事，定性交給判斷層：

```
{ 數值: 6.2%, 門檻: 5%（來源：X 研究）, 適用性: 該研究族群為 Y，本學員條件符合/不符合 }
```

事實層**不**輸出「心率漂移偏高」這種已定性的結論。理由：若閾值歸事實層，「這個門檻適用於你嗎」這個判斷會被偷藏進事實層；若閾值全歸判斷層，則 N-3 的研究成果被浪費，AI 每次重新發明門檻，飄移風險回歸。**門檻的適用性就是門檻的信賴度**——故此規則與 §7.3 的三欄位契約是同一個形狀，不是額外規則。

**軟性輸入採半落地**。新增 `context_notes`（自由文字 ＋ 日期範圍 ＋ `athlete_id`），記錄出差、睡眠不足、工作壓力、心情等規則算不出的情境。**不預先設計類型與嚴重度等結構化欄位**——現階段尚不知「嚴重度」該如何分級，硬訂 schema 等於在假設上建構（與 §1「外部課表本輪僅預留欄位」同一理由）。自由文字讓 AI 讀得懂，日期範圍讓規則層能與活動／wellness 對齊；累積數十筆後回看實際內容，再決定是否結構化。

> **不落地為何不可行**：§6.8 保留課表版本歷史是為支撐「原計畫 vs 實際執行」的偏差比對迴圈。若「為什麼偏差」只存在於對話中，三個月後回看只見「這週漏了三課」而不見「因為出差」，該迴圈做不完整。

⚠️ **硬邊界：軟性輸入永不進事實層，僅作判斷層的補充輸入。** 它無法驗證（學員自述睡不好，系統無從查證），若讓它參與規則計算，等於在事實層開一個沒有信賴度可標的洞，直接違反 §7.3 的硬規則。

### 7.6 人設的兩層結構：行為約束層與風格層（⏸️ 風格層已擱置，待未來有空檔再研究）

> **狀態（2026-08-21）**：構想與初步問題分析已記錄完成，**目前擱置不開發**。已識別出兩個尚未解決的問題（見下方），未來啟動前須先處理，不可直接依現有內容實作。

除了事實層／判斷層的分工，**人設本身也應拆成兩層**，兩者生命週期與風險等級不同：

| 層 | 內容 | 可否由使用者自訂 | 開發時程 |
|---|---|---|---|
| **行為約束層** | 每項建議須引用具體數據來源、無資料時明說不臆測、涉及傷病症狀不給醫療建議、稱呼一致（N-1）| ❌ 不可覆寫 | Phase 3 本體 |
| **風格層** | 語氣（嚴厲／溫和）、稱謂口吻、是否用比喻與鼓勵、回覆長度與細節密度、幽默感 | ✅ 可自訂 | **延後至專案後期** |

**動機**：只有行為約束的教練雖然可信，但回答容易枯燥乏味、像在讀報表。真實教練的價值有一部分來自溝通風格與人味，能維持使用者的長期黏著度——這對需要持續數月的馬拉松訓練週期尤其重要。

**構想的具體形式**（2026-08-21 討論）：預期做**兩條路**——「專業使用」與「輕鬆使用」，前提是**行為約束層永遠優先**，風格變化不可違背教練的專業度。

**設計原則**：
- **風格層只影響「怎麼說」，不得影響「說什麼」**——嚴厲或溫和的教練，對同一份數據應給出**相同的訓練建議**，只有措辭不同。若切換風格會改變建議內容，代表風格層洩漏到了判斷層，屬實作錯誤
- 風格設定存 `athlete_profile` 可配置欄位（比照 §6.7 個人化恢復閥值的既有作法），非寫死在 system prompt
- ⚠️ **行為約束層永遠優先**：風格層不得覆寫任何安全性約束。例如使用者設定「幽默風趣」，也不能把傷病警訊講成玩笑；設定「極簡回覆」，也不能省略無資料時的誠實揭露
- 需驗證風格切換確實不改變建議內容（同一份數據跑不同風格設定，比對建議的實質差異）

#### 已識別的問題與待研究方向（⚠️ 尚未解決，開發前須先處理）

**問題 1：「不可違背專業度」無法直接執行**
此約束方向正確，但「專業度」未被定義，實作時無從遵守、驗證時無從測試。需換成可執行的形式。

**問題 2：風格中立性的假設在壞消息上會破**
「同一專業判斷可用兩種風格說出，聽者接收到的資訊量相同」——此假設在多數情況成立，但「輕鬆」風格的本質有一部分就是**降低壞消息的衝擊**，而降低衝擊與完整傳達風險在特定情境直接衝突：

| 情境 | 嚴厲版 | 輕鬆版 | 評估 |
|---|---|---|---|
| 配速比目標慢 5% | 「這次沒達標，原因是 X」 | 「這次差一點點，可能是 X 影響」 | ✅ 純措辭差異，無問題 |
| 連續 5 天訓練、HRV 偏低 | 「必須休息，你在過度訓練邊緣」 | 「身體有點累喔，休息一下吧～」 | ⚠️ 緊急程度被稀釋 |
| 膝蓋疼痛三週未緩解 | 「停止跑步，去看醫生」 | 「膝蓋還在痛的話，找個醫生看看比較安心～」 | ❌ 安全問題，語氣不該軟化 |

**待研究的解法方向：嚴重度熔斷機制**
與其寫「不可違背專業度」這種無法驗證的約束，改為：**當規則引擎輸出的旗標達到某嚴重度門檻時，風格層自動停用，一律採行為約束層的直述語氣**。即「風格層的自由度與訊息嚴重度成反比」——日常回饋可有人味，警訊必須平鋪直敘。

此方向的優點：
- **可驗證**：能寫測試——餵入 `injury_risk: high` 旗標，斷言不論風格設定為何，輸出皆包含明確停練建議
- **界線畫在資料而非語感上**：不需 AI 判斷「這樣講算不算違背專業」，由規則引擎的嚴重度欄位直接決定
- **與既有架構一致**：屬 §7.3「事實層產出旗標、判斷層據以決策」的延伸，風格層僅多吃一個「嚴重度」輸入

**仍未解的爭點**（未來啟動時須先釐清）：
1. 嚴重度門檻怎麼訂、由誰訂——回到 N-3 科學依據的範疇
2. **兩條路是同一使用者可切換，還是給不同類型的使用者？** 若為後者，「輕鬆使用」的目標客群很可能是新手，而新手恰是最需要清楚警訊、最易忽略過度訓練徵兆的一群——此張力須一併處理
3. 熔斷是二元開關還是漸進調節（風格強度隨嚴重度線性遞減）

**為何延後**：風格層的前提是判斷層已經穩定——建議內容本身還會變動時就調風格，等於在流沙上蓋房子，且難以分辨「回答變好」是風格改善還是判斷改善。故 N-4／N-3／訓練品質評估定案並實作完成後才啟動，列為 Phase 4。

## 8. 個人資料存放位置

個別學員的資料、課表與訓練紀錄**不寫入本計畫**，一律放在 `output/`（已列入 `.gitignore`，不進版控）：

| 檔案 | 內容 | 將來對應資料表 |
|---|---|---|
| `output/athlete_profile.md` | 學員基本資料、目標賽事、訓練偏好、個人限制 | `athlete_profile` |
| `output/current_training_plan.md` | 當期課表排程與配速指引 | `training_plan` |
| `output/training_log.md` | 實際執行紀錄與教練觀察 | `activities` / `daily_wellness` |

> 這些 md 是**資料庫就緒前的過渡方案**。Phase 1 資料匯入完成後應遷移進 SQLite，避免同一份資料存在兩處而互相矛盾。

編號慣例：本檔與 TODO.md 用 `P-`（專案層級待確認事項）；`output/athlete_profile.md` 用 `A-`（學員個人層級）。兩組編號各自獨立，不互相延續。
